## Revision 2 – Fixture-Eingaben des JUnit-Tasks

Nach dem ersten Kandidatenreview wurde eine zusätzliche eigene Gradle-Cache-
Gegenprobe ausgeführt. Sie zeigte eine tatsächliche Lücke: Die Java-Prüfung der
externen Originalfixtures konnte nach einer Änderung ihrer Quelldaten als
`UP-TO-DATE` gelten. Der vorherige Python-Exec hatte diese Dateien jedes Mal
geprüft. Deshalb deklariert `interlis-cli/build.gradle` jetzt das Fixtureverzeichnis
und `stabilization-contract.cjs` als benannte relative Task-Eingaben.
Der erste unabhängige Bericht unter `build/review/L0B-1/attempt1-review.md` gilt
ausschliesslich für den ersten Kandidaten; diese Codeänderung benötigt einen
neuen vollständigen unabhängigen Review.

Reale Gegenprobe in einem eigenen temporären Archive-Checkout, keine Produkt-
oder Goldenquelle geändert; jeweils **ohne** `--rerun-tasks`:

1. `./gradlew :interlis-cli:test --tests '*OriginalViewFixtureContractTest'`
   mit unveränderten Daten: Exit **0**, `input-cache-baseline.log`.
2. Nur im temporären Checkout ein Newline an
   `view_AcceptBasicSelectionViewDef.ili` angehängt; identischer Task auf dem
   ersten Kandidaten: Exit **0**, `test UP-TO-DATE` – nachgewiesenes Fehlgrün,
   `input-cache-red.log`.
3. Korrigierte Task-Deklaration eingesetzt; unveränderte Daten erneut mit
   Exit **0** geprüft (`input-cache-fixed-baseline.log`). Dann nur die Fixture
   verändert: derselbe Task wird tatsächlich ausgeführt und endet mit Exit **1**,
   `OriginalViewFixtureContractTest` / `AssertionFailedError`,
   `input-cache-fixed-negative.log`.
4. Fixture wiederhergestellt und mit Exit **0** geprüft
   (`input-cache-js-baseline.log`); danach nur den Text eines eingebetteten
   Originalfixtures im JS-Block verändert: Exit **1**, derselbe tatsächliche
   Assertionfehler, `input-cache-js-negative.log`.
5. Alle temporären Daten wiederhergestellt, vollständiger CLI-JUnit-Lauf:
   Exit **0**, `input-cache-restored.log`.

Auf der korrigierten Produktrevision erneut frisch:
`JAVA_HOME=/Users/stefan/.sdkman/candidates/java/25.0.3-tem ./gradlew check conformanceCheck --rerun-tasks`
→ Exit **0**, **728 JVM-Tests**, 0 Failures/Errors/Skips, volle unveränderte T2-
Bilanz, 59 Evidenztests und SDK-Beispiel; 44 Tasks, 1m 47s,
`verification-r2.log`. Die exakte Alt-/Neu-Parität wurde danach erneut geprüft.
Die Testmethoden, Erwartungen und Referenzpins wurden für diese Revision nicht geändert.

## Revision 3 – relativer Cachepfad

Eine weitere eigene Gradle-Diagnose bestätigte, dass `new File(relative)` im
Daemon relativ zu `~/.gradle/daemon/9.8.1` aufgelöst wird, während der alte
Pythonpfad relativ zum Repository arbeitete (Diagnoseprobe Exit **1**,
`relative-cache-root-diagnosis.log`). Der Cacheprovider wird deshalb jetzt
einmal mit `rootProject.file(...).absolutePath` aufgelöst. Archivhashprüfung,
Extraktion und Fixturecache verwenden dadurch dieselbe absolute Adresse,
auch bei einem relativen `CONFORMANCE_CACHE`.

Reale Prozessprüfungen im temporären Checkout mit
`CONFORMANCE_CACHE=build/relative-conformance-cache ./gradlew prepareConformanceSuite`:
falsches Archiv am relativen Repositorypfad → Exit **1** / Hashfehler
(`relative-cache-negative.log`); korrekt gepinntes Archiv dort → Exit **0**
(`relative-cache-positive.log`). Der extrahierte Java-Runner ist bytegleich
mit dem gepinnten Runner (SHA-256 beider Dateien
`0f83ff36580d247467adecfdf5edda73fb3f2dc641a81cb5138c490e711fe5ff`).

Danach wiederum frisch `./gradlew check conformanceCheck --rerun-tasks` mit
JAVA_HOME wie oben → Exit **0**, **728 JVM-Tests**, 0 Failures/Errors/Skips,
vollständige unveränderte T2-/Normbewertung, 59 Evidenztests und SDK-Beispiel;
44 Tasks, 1m 48s, `verification-r3.log`. Auch die exakte Parität wurde erneut
geprüft (`parity-r3.log`). Diese zusätzliche Buildkorrektur verlangt wiederum
einen unabhängigen Review des aktuellen Kandidaten; frühere Urteile ersetzen ihn nicht.
